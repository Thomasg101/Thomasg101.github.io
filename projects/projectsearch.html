    01 / Context

    The photo was always taken. Finding it again was the problem.

    Envelope work generates thousands of site photographs across review visits, and the useful ones are rarely labelled. A folder tree can tell you which project and roughly which day a photo belongs to; it cannot tell you which frame shows the debonded base flashing at the northeast corner.

    The constraint that shaped everything: an engineering photo share is a working record. It cannot be reorganised, renamed, or copied into somebody's tool to make search convenient.

    02 / What I built

    A local index over photos that stay exactly where they are.

    • A read-only indexer that walks a share and writes one structured record per photo — nothing is moved, copied, or renamed.
    • A vision pass that describes what is visible: caption, setting, level, room, components, materials, conditions with estimated severity, and any verbatim text in the frame.
    • A per-field confidence rating, so a weak guess is visible as a weak guess instead of quietly becoming a fact.
    • A four-stage retrieval pipeline behind a plain-English query box.
    • A 3D building view that places every photo on a model of the real footprint.

    03 / How a search runs

    Four stages, each one narrowing for a stated reason.

    1. Semantic. Embed the query and rank records by cosine similarity, so a description matches a photo that uses none of the same words.
    2. Lexical. Run BM25 over SQLite FTS5, which is what actually finds “RTU-3” when someone types the tag stencilled on the unit.
    3. Fusion. Merge both rankings, because the two stages fail in different places and rarely fail together.
    4. Rerank. A final model pass re-orders the shortlist against the full structured record rather than the caption alone.

    04 / Structured vision records

    One record per photo, every field separately rated.

    Every indexed frame becomes a record with its own confidence per field. Low-confidence locations stay visible in the interface but are excluded from the index, so a guess never silently becomes a search result.

    05 / Building View and floor inference

    Where a photo was taken, argued from ranked evidence.

    Every photo is placed on a three.js model built from the real OpenStreetMap footprint — a floor stack, one GPS marker per photo, orbit and fly-to, and a floor rail that cuts away everything above the level you are looking at.

    Which floor a photo belongs to comes from six ranked evidence sources: a manual override, a level read in the photo itself, a suite number, the folder name, the kind of space, and a time-ordered walk inference. The interface always states which source it used, and the inference is deliberately timid — it backs off when GPS altitude disagrees with the evidence.

    06 / Runs anywhere, installs nothing

    A launcher that survives a locked-down laptop.

    A launcher provisions a private Python through uv, so the tool runs without admin rights on a managed machine. Parallel tagging workers share a rate limiter that pauses every worker on HTTP 429, so a rate-limit storm never leaves holes in the index.

    07 / My role

    Built during my Entuitive co-op, end to end.

    I shaped the use case, designed the record schema and the confidence model, implemented the indexer, the retrieval pipeline, the API, and the browser interface including the 3D building view, and packaged the launcher. The tool is being evaluated for engineering workflows; it is not presented here as a released product.
